Research Knowledge System

A personal knowledge base where every answer is traceable to a paper you actually own.

Cloud AI for the public corpus. Local AI for unpublished work. One file system shared across both.

📖 This is an interactive walkthrough. Click buttons and dropdowns throughout to see how each part of the system works. All examples use a generic motor-learning topic.

Philosophy

Why this system exists

Researchers accumulate hundreds of PDFs. Context evaporates between sessions. Large language models hallucinate citations that look real. Unpublished work must never touch cloud AI.

This system solves all three with one design rule:

The wiki is the evidence layer. The LLM is the reasoning layer.
Every answer is grounded in a paper that physically exists in papers/. Cross-paper synthesis lives in wiki/overviews/. Confidential drafting runs on a local LLM that the cloud cannot see.

Non-negotiable

The Four Rules

These apply to every cloud agent in every conversation. They prevent hallucination and keep every claim traceable.

1No web search. Never use external search to fill gaps. The point of this wiki is that every answer is grounded in papers we actually own.
2Answer from the wiki first. Use sources/ and wiki/ as the only sources of truth.
3If the wiki is insufficient, re-read the PDF. Go to papers/{stem}.pdf and extract more detail. Then update the wiki.
4If the wiki has no paper on the topic, say so. "I don't have a paper on this — please give me the PDF." Do not improvise.

Architecture

Three spaces × Two tiers

Everything lives in one folder on your machine. What changes is which AI is allowed to read each part.

cloud-ok

📚 LIBRARY

papers/, sources/, wiki/, index.md

Permanent knowledge base. Built by cloud agents. Read by everyone.

cloud-ok

💡 EXPLORATION

explorations/idea-notes/
explorations/active/{slug}/

Pre-project incubator. No unpublished hypotheses.

local-only

🔒 PROJECT

projects/{slug}/

Grant · paper_in_prep · review_article. LOCAL LLM ONLY.
Exception: library_ingest projects → cloud-ok.

Routing

Confidentiality is a routing rule

The files are on the same machine. What changes is the AI lane.

✓ Cloud AI may read

  • papers/ (published corpus)
  • sources/, wiki/, overviews/
  • explorations/ (public-facing)
  • library_ingest project briefs
  • index.md

✗ Local LLM only

  • projects/{slug}/ (grant, paper_in_prep, review)
  • papers/under-review/
  • explorations/active/*/_pdfs/
  • Any file with confidential_tier: local-only
Hard refusal: If a cloud agent encounters a confidential path, it must refuse — even if the user says "do it here anyway." This is the only non-overridable rule in the routing system.

2. Quick Scout — find new papers

Add papers to the wiki in one click. Searches PubMed, arXiv, bioRxiv, and Semantic Scholar against a topic.

Build phase

Quick Scout

Run a paper scout campaign in one click. New topic scouts are saved under scouts/{slug}/.

What happens when you click Run Scout
  1. Creates scouts/{slug}/Scout_Brief.md with your topic and keywords.
  2. Queries PubMed, arXiv, bioRxiv, and Semantic Scholar in parallel.
  3. Saves all candidates to scouts/{slug}/candidates/{date}/.
  4. Generates a triage approval board so you can decide which PDFs to download.

Nothing enters the wiki yet — human approval is required first.

The scout history

Every previous scout campaign is preserved in scouts/ with its keywords. Click any past scout to re-run it or to see overlap with your current topic.

📥 Scopus CSV Import

Import papers from a Scopus search directly into a scout candidate batch — no API key required.

How to use

  1. In Scopus, run your search, select results, click Export → CSV.
  2. Make sure these columns are checked: Title, Authors, Year, DOI, Abstract. Also recommended: Source title, Author Keywords, PubMed ID, Link.
  3. In the dashboard Quick Scout section, click 📥 Import Scopus CSV.
  4. Choose your CSV file, then either add it to an existing scout or create a new one (enter topic + keywords).
  5. Click Import. The candidates appear as a batch under scouts/{slug}/candidates/{date}/.
  6. Click the ? next to the button for a reminder of required CSV columns.

After importing, select the scout in the PDF/Ingest dropdown and use 📋 Triage to generate criteria pre-filled with your keywords.

📋 Triage Criteria — keyword pre-fill

When you click 📋 Triage in the PDF/Ingest panel, the criteria template is now pre-filled with the topic and keywords from the selected scout.

  • Keywords come from the Must-include keywords section of the scout's Scout_Brief.md.
  • For scouts created via Quick Scout, the keywords you typed are saved automatically.
  • For Scopus CSV imports, the keywords you entered in the import dialog are used.
  • If you switch to a different scout in the dropdown, the criteria template refreshes to match.
  • You can always edit the criteria before saving.

✨ Synthesize

After ingesting papers, click ✨ Synthesize in the PDF/Ingest panel to generate a wiki/overviews/ synthesis prompt pre-filled with keywords from the selected scout. The prompt is ready to paste into Claude Code or Codex CLI as the Synthesizer agent.

5. Drafter homework flow — the LLM amplifies, not replaces

The Drafter cannot write from a blank page. You must do the homework first.

This is by design. Without your own framing in user-drafts/, the LLM has nothing to amplify and the output collapses into generic boilerplate. The system forces you to think first.

1. User skeleton
user-drafts/{section}.md
→
2. Wiki context
wiki_context.md
→
3. Drafter amplifies
Drafts/{section}.md
→
4. /compare → iterate
side-by-side review

Step 1 — Write your own skeleton

Open user-drafts/{section}.md and write 5–10 lines:

  • The central claim of this section
  • The framing or narrative angle
  • Which papers to cite (by wiki page name)
  • What contradictions or limitations to acknowledge

Why: This is the user's contribution. The LLM reads it as instructions, not as content to copy.

Step 2 — Load wiki context

Click "Analyze wiki relevance" with topic keywords. pre_drafter.py scans sources/ and wiki/ for relevant pages and writes:

projects/{slug}/wiki_context.md

Why: The Drafter only cites papers in wiki_context.md. No invented citations. No hallucinations.

Step 3 — Drafter reads + writes

Click "Draft — choose section". The Drafter loads:

Project_Brief.md
wiki_context.md          ← from step 2
user-drafts/{section}.md ← from step 1
Drafts/{section}.md      ← prior version (if any)

Then writes a new version that builds on your skeleton, cites real wiki papers, and respects your framing.

Step 4 — Compare and iterate

Inside the Drafter session:

  • /compare — side-by-side: your draft vs Drafter's draft
  • /save — accept the new version → Drafts/{section}.md
  • /export-docx — Word output with citations
  • Edit user-drafts/, run again

Each iteration: you sharpen the skeleton, the Drafter amplifies.

If you skip Step 1: the Drafter will run, but the output is generic — paragraphs that could be in any paper. The user's contribution is the skeleton. The LLM's contribution is the prose density and citation grounding. Both halves are required.

Example: user-drafts/introduction.md (skeleton, ~8 lines)
## Central claim
Cerebellar plasticity is necessary, not just sufficient, for motor learning.

## Framing
Open with the long-running uncertainty: necessity vs sufficiency.
Then narrow to recent loss-of-function evidence.

## Papers to cite (wiki page names)
- cerebellar-circuits/{paper1}.md
- methods/{paper2}.md
- overviews/cerebellar-learning.md  (synthesis)

## Limitation to acknowledge
Optogenetic timing constraints — cite {paper3}.md

## End with
The gap our work fills (no specific results yet).

The Drafter reads this and writes a real introduction following your structure — but with real citations from your wiki and prose that fills the gaps.

6. Scout brief system — zero identity leakage

How does a confidential project search the public paper corpus without leaking what it's about?

📁 Project_Brief.md
local-only
→
🤖 Local LLM
writes sanitized brief
→
🔍 Self-simulation
"can the project be guessed?"
→
📤 scouts/
cloud-ok export

The brief must NOT contain

  • The specific hypothesis
  • Unpublished data or pilot results
  • PI name, lab name, institution
  • Grant aims or specific objectives
  • The project slug or title
  • Any distinctive transgenic line or rare model

The brief MAY contain

  • Broad scientific field (e.g., "cerebellar circuit plasticity")
  • Standard MeSH terms used across the field
  • Names of widely-cited public researchers
  • Generic year range
  • Generic exclusion criteria
  • Sources to search

Server-side validation (before export)
  1. Frontmatter must contain simulation_passed: true. Otherwise export blocked.
  2. The project slug must not appear anywhere in the body. Otherwise export blocked.
  3. Only then is the file copied to scouts/project-{slug}/Scout_Brief.md.

Result: Even if the local LLM violates the rules, the server catches it before any text leaves the confidential zone.

8. Mendeley integration — two systems, one source of truth

The wiki is your reading memory. Mendeley is your citation manager. Same PDFs, no manual duplication.

📚 LLM-Wiki

Curated reading memory

  • Papers you have read + synthesized
  • Structured source summaries
  • Cross-paper overviews
  • Reasoning substrate for LLMs

Selected. Read. Synthesized.

📖 Mendeley

Citation manager

  • Reference library for Word
  • Automatic citation insertion
  • BibTeX export
  • Personal reference catalog

Comprehensive. Citation-ready.

Two-way sync via scripts

Mendeley bridge

After ingesting a paper, sync it to Mendeley

When a PDF enters papers/ via the Ingester, you decide whether to also push it into Mendeley's watched folder.

sync_to_mendeley_watch.py
Copies the canonical papers/{stem}.pdf into _system/mendeley/watch/ — Mendeley's configured watched folder. Mendeley auto-imports it on its next scan. 
python3 scripts/sync_to_mendeley_watch.py --paper papers/{stem}.pdf

Direction: wiki → Mendeley (one-way).
Mendeley's internal storage is read-only from the wiki side — never renamed or moved.

audit_mendeley_export.py
Reads Mendeley's BibTeX export and compares against the wiki. Finds:
  • Papers in Mendeley but missing from the wiki (candidates to ingest)
  • Papers in the wiki but missing from Mendeley (candidates to push)
  • Metadata mismatches (DOI, year, author)
python3 scripts/audit_mendeley_export.py

Audit-only — never modifies Mendeley. Generates a report in _system/mendeley/review/.

Why keep them separate?

Each system is optimized for a different job:

  • Mendeley stores every paper you might cite. It plays nicely with Word's cite-while-you-write. But its database is opaque to LLMs.
  • LLM-Wiki stores only papers you've actually read + synthesized. Plain markdown, queryable, citable by LLMs, version-controlled.

Trying to make one system do both means losing what makes each good. The sync scripts let you have both without duplicating work.

The boundary rule: Mendeley is read-only from the wiki's perspective. The wiki never renames, moves, or deletes anything in Mendeley's internal folders. Sync is one-way: wiki → Mendeley watch folder. Mendeley does its own import on its own schedule.

v2.3 · 2026-05-15

What's new in v2.3

This release introduces project-level governance and confidential data tracking on top of the existing wiki / project / exploration architecture: an admin mode protecting privileged edits, project managers with mailto integration, Google Drive data tracking with rollback, a meeting system, and a Phase 3 LLM sync workflow that proposes — but never auto-applies — updates to project planning artifacts.

Detailed reference for each item: _system/docs/features/ · one markdown file per feature.

v2.3 · Dashboard layout

Layout refresh

The Snapshot panel now sits in a full-width row at the top, and Active workspaces fills the row below — one project card per row instead of being squeezed next to Snapshot. Inside each card the 10 count chips arrange themselves in a single horizontal flex row that scales with screen width.

Why: as projects multiply, the previous 2-column layout pushed each card into a narrow column and forced excessive vertical scroll.

v2.3 · People

Project managers

Each project can have one or more managers (name + email), stored in Project_Brief.md frontmatter under a managers: block. A badge in the bottom-right of every project card shows manager names.

Clicking the badge opens a popup with:

  • One row per manager with a checkbox, name, and clickable email (mailto:).
  • A Select all toggle when there are 2+ managers.
  • An 📧 Email selected managers button that opens a single mailto: with all checked addresses comma-joined.

Editing managers is gated by admin mode — an ✎ button only appears once admin is unlocked.

Frontmatter format: 
managers:
  - name: "Alice Lee"
    email: "alice@example.com"
  - name: "Collaborator A"
    email: "alice@example.com"

v2.3 · Governance

Admin mode (PIN-protected) with email recovery

The top bar has a 🔒 Admin: Off toggle. Privileged edits (currently editing project managers, with more to come) require a 4–8 digit PIN. A recovery email is collected at setup so the PIN can be reset later.

  • First-time setup: the modal asks for a PIN (entered twice) and a recovery email. Stored at _system/admin/admin_config.json (gitignored, chmod 600).
  • Unlock: click the toggle, enter PIN, verified server-side. Tab becomes admin-unlocked (sessionStorage only — closing the tab locks again).
  • Forgot PIN: confirm the recovery email; the server generates a 6-digit code (15-min expiry), emails it via SMTP if configured, otherwise prints it to the dashboard-server terminal as a local fallback. Enter the code + new PIN to reset.
Security: PBKDF2-HMAC-SHA256 with 200 000 iterations and per-install salt; hmac.compare_digest for verification; dashboard server binds to 127.0.0.1 only.

SMTP env vars for real email: DASHBOARD_SMTP_HOST, _PORT, _USER, _PASSWORD, _FROM. Gmail requires an App Password, not your account password.

v2.3 · Drill-down

Count-chip file list popup

Every count chip on a project card is now clickable. Clicking opens a popup listing the actual files in the corresponding folder. Each row opens that file in its default macOS app.

Buckets: candidates / triage-reports / approval-boards / drafts / claim-logs / candidate-batches / notes / data-updates / critiques / figure-plan / meetings.

For data-update rows, the popup adds a Reassign… button (see next section).

v2.3 · Confidential data tracking

Data updates with Google Drive integration

The + Data update button on each project card opens a structured form that records a new data event. The actual data file is moved into a project-specific subfolder of Google Drive named LLM_project_manager/ — the only Drive location the LLM is allowed to touch.

Canonical filename

fig-1A_brief-slug.csv · prelim_… · unspecified_…

The brief description (3–6 words) is required and drives the slug.

Two modes

New data — fresh .md + moved file.
Adding to existing — old file → archive/{name}_{timestamp}.zip, new file replaces canonical name, note appended to existing .md.

Append-only CHANGELOG

LLM_project_manager/CHANGELOG.md records every CREATE / UPDATE / REASSIGN / RENUMBER / RESTORE with timestamp + reason.

Source of truth: the figure field in each data-update's frontmatter is authoritative. Physical filenames mirror it but are display-only — they will be renamed on reassignment.

If gdrive_path is missing for a project, the modal shows an inline Set Google Drive path… button that opens a native macOS folder picker and writes the field to Project_Brief.md.

v2.3 · Figure organisation

Reassign & bulk renumber figures

As projects evolve, figures get reorganised. Two operations cover the common cases without losing history:

  • Reassign (single data-update): change figure/panel for one record. Server rewrites frontmatter + renames the canonical file (unspecified_foo.csv → fig-2A_foo.csv) + appends a CHANGELOG line.
  • Renumber figures (bulk): map Fig 2 → Fig 3, Fig 3 → Fig 2 (any number of rows). A 2-pass rename via temporary names handles swap-style cases safely. Server updates all matching data-updates, their files, and the rows in figure-plan.md.

Both operations require a reason that is recorded in CHANGELOG, so the audit trail is preserved.

v2.3 · Rollback

Archive viewer & restore

When a data file is replaced by a newer version, the previous file is automatically compressed into LLM_project_manager/archive/. The 📦 Archive button on each project card lists those zips and offers a Restore action per row.

Restore extracts the zip back into LLM_project_manager/. If a file with the original name already exists, the restored file is suffixed with _restored_{timestamp} to avoid clobbering current data.

v2.3 · Meetings

Meeting system (ICS + macOS Calendar + append-only notes)

Each project can schedule meetings directly from the dashboard. The + Meeting button opens a modal that captures type, title, datetime, duration, attendees (project managers auto-checked + ad-hoc additions), location, and agenda.

On save, the system writes:

📝 Meeting record

projects/{slug}/meetings/{date-type-slug}.md with frontmatter + agenda + notes history.

📅 ICS invite

Standard RFC-5545 .ics file next to the .md. Floating local time. Recipients with emails are listed as ATTENDEE entries.

🗓 macOS Calendar

Event added to the default writable calendar via AppleScript. Optional toggle in the modal.

Meeting types — default table / progress / collaborator — are extensible via the modal's + New type action, persisted in _system/admin/meeting_types.json.

The Meetings button on each card lists all meetings; each row has + Note (append-only markdown section) and .ics (re-open invite) buttons.

v2.3 · Phase 3

LLM sync proposals (approval workflow)

Two new local-LLM roles read recent data-updates / meeting notes and propose mechanical changes to project planning artifacts. The LLM never edits files directly — it writes a proposal that the user reviews item by item.

local-only

🤖 data-sync

Reads recent data-updates/*.md + planning artifacts. Proposes status updates and Decision_Log entries.

Prompt: subagents/12-data-sync.md

local-only

🤖 meeting-sync

Reads recent meetings/*.md + planning artifacts. Proposes decisions logged + figure/experiment shifts.

Prompt: subagents/13-meeting-sync.md

Apply with checkboxes

The Proposals button lists generated proposals; each action has a checkbox + summary. Server applies selected items mechanically (regex / YAML edits) and appends an ## Applied audit section.

Action vocabulary: figure_plan_status_update · experiment_roadmap_status_update · figure_plan_add_row · experiment_roadmap_add_row · decision_log_append · note. Every action carries source_files for traceability.

Apply uses mechanical text edits, not the LLM — so an Apply can never itself hallucinate. The LLM only proposes; the user approves; the server executes.
